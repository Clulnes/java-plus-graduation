# Дипломный проект: ExploreWithMe (Этап 2 — Микросервисы)

Приложение-афиша для поиска и публикации событий.
В рамках второго этапа монолит основного сервиса был декомпозирован на независимые микросервисы с использованием Spring Cloud.

---

## 1. Архитектура и структура модулей

Проект разделён на независимые сервисы, которые объединены в родительские модули:

### Инфраструктура (`infra/`)
* **`discovery-server`** (порт 8761) — Eureka Server. Микросервисы регистрируются здесь и находят друг друга без захардкоженных портов.
* **`config-server`** — сервер конфигураций. Хранит и отдаёт настройки микросервисов из папки `infra/config-server/src/main/resources/config/`.
* **`gateway-server`** (порт 8080) — Spring Cloud Gateway. Единая входная точка для всех внешних запросов (включая автотесты). Он маршрутизирует запросы на нужный сервис по URL.

### Бизнес-сервисы (`core/`)
* **`main-service`** — сервис мероприятий. Отвечает за события, категории и подборки.
* **`user-service`** — сервис пользователей. Отвечает за создание, поиск и удаление пользователей администратором (`/admin/users`).
* **`request-service`** — сервис заявок. Управляет подачей, отменой и модерацией заявок на участие в мероприятиях (`/users/{userId}/requests`).
* **`comment-service`** — сервис комментариев (дополнительная функциональность). Позволяет оставлять комментарии к событиям, отвечать на чужие комментарии и модерировать их.
* **`interaction-api`** — общий модуль, где лежат контракты: общие DTO и интерфейсы OpenFeign для межсервисного общения.

### Статистика (`stats/`)
* **`stats-server`** — сервис сбора и отдачи статистики просмотров.
* **`stats-client`** — библиотека-клиент со встроенным RetryTemplate для повторных запросов, если сервис статистики временно недоступен.

## 2. Межсервисное взаимодействие (Внутренний API)

Вместо прямых вызовов методов в одном коде сервисы теперь обращаются друг к другу по HTTP через **OpenFeign**:

1. **`UserClient`** (обращения к `user-service`):
    * `GET /internal/users/{userId}/exists` — проверка существования пользователя перед созданием заявки или комментария.
    * `GET /internal/users/{userId}` — получение данных пользователя (имени).

2. **`EventClient`** (обращения к `main-service`):
    * `GET /internal/events/{eventId}` — получение информации о событии (статус публикации, лимит участников, ID создателя, заголовок).
    * `POST /internal/events/{eventId}/increment-confirmed` — увеличение числа подтвержденных участников при одобрении заявки.
    * `POST /internal/events/{eventId}/decrement-confirmed` — уменьшение числа подтвержденных участников при отмене заявки.
    * `POST /internal/events/{eventId}/add-confirmed?count={count}` — массовое обновление подтвержденных заявок.

## 3. Маршрутизация в Gateway

Клиенты обращаются только на порт `8080`. Шлюз распределяет запросы:
* Запросы пользователей (`/admin/users/**`) ➔ `user-service`
* Запросы по заявкам (`/users/*/requests/**`, `/users/*/events/*/requests/**`) ➔ `request-service`
* Запросы по комментариям (`/users/*/events/*/comments/**`, `/events/*/comments/**`, `/admin/comments/**`) ➔ `comment-service`
* Все остальные запросы к афише (`/events/**`, `/categories/**`, `/compilations/**`) ➔ `main-service`
